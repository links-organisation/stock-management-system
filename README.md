# Stockroom — Shop Stock Management System

A capstone project: a Spring Boot REST API + Angular SPA for a shop to log in, register
products, sell them, track stock, search inventory, view dashboard KPIs, keep a full
audit trail of who did what, and generate database-level invoices on every sale.

See [`.docs/Stock_Management_Project_Specification.md`](.docs/Stock_Management_Project_Specification.md)
for the full spec this implements.

## Stack

- **Backend** — Java 21, Spring Boot 4.1.1 (Web, JPA, Validation), H2 (file-based), manual
  auth with standalone `spring-security-crypto` (BCrypt) — no Spring Security framework.
- **Frontend** — Angular 22, standalone components, template-driven forms, no UI kit.

## Running it locally

Two servers, both need to be running.

**Backend** (port 8080):
```bash
cd backend
./mvnw spring-boot:run
```
On first run this creates `backend/data/stockdb.mv.db` and seeds one account per
role, plus two categories (Beverages, Snacks) and three sample products:

| Username | Password | Role |
|---|---|---|
| `admin` | `admin123` | Super Admin (the only one — see Roles below) |
| `shopadmin` | `admin123` | Admin |
| `seller` | `seller123` | Seller |
| `compta` | `compta123` | Compta |

**Frontend** (port 4200):
```bash
cd frontend
npm install   # first time only
npx ng serve
```
Then open `http://localhost:4200` and sign in with any of the accounts above.

The frontend's CORS/API base URL assumes the backend is on `localhost:8080`
(see `frontend/src/app/core/api-config.ts`).

### Running the test suites

```bash
cd backend && ./mvnw test
cd frontend && npx ng test --watch=false
```

## Roles

All entity IDs are UUIDs. Every user has exactly one role, checked server-side on
every mutating request (there's still no Spring Security — the acting user's id
travels in the request body/query, same as before; the backend now also loads
that user and checks their role before proceeding).

| Feature | Super Admin | Admin | Seller | Compta |
|---|---|---|---|---|
| Manage products/categories | ✓ | ✓ | – | – |
| Adjust inventory | ✓ | ✓ | – | – |
| Sell (create sales) | ✓ | ✓ | ✓ | – |
| View dashboard/history/invoices | ✓ | ✓ | ✓ | ✓ |
| Manage users | ✓ (anyone but Super Admin) | ✓ (Seller/Compta only) | – | – |

There is exactly one Super Admin — the account seeded by `DataSeeder`. No API path
can create, promote a user to, or edit a Super Admin account; `POST /api/users` and
`PUT /api/users/{id}` both reject a `SUPER_ADMIN` role outright. Every user can
change their own username/password from **My account** (`/account`) regardless of
role.

## Demo walkthrough (~8 minutes)

A suggested order that touches every functional requirement (F1–F8) and shows
traceability of the acting user throughout.

1. **Login (F1)** — Try a wrong password first (shows the error state), then sign in as
   `admin`. Point out the session persists across a refresh (stored via `AuthService`,
   not a token — matches the spec's "no Spring Security" constraint).
2. **Products (F2, F5)** — Register a new product with a category. Edit its selling
   price. Use the search box and the category filter together. Point out the low-stock
   card (red border) for Potato Chips.
3. **Sell (F3)** — Add two or three products to a sale, adjust quantities, remove a
   line, then complete the sale. Show the stock quantities drop immediately on the
   Products page afterward.
4. **Inventory (F4)** — Adjust a product's quantity to correct a physical count
   (with a reason comment). Show the stock value recalculate.
5. **History (F7)** — Open the audit trail: filter by type (e.g. `SALE`), by product,
   and by a date range. Point out every row shows who performed it (`performedBy`).
6. **Invoices (F8)** — Open the invoice generated by the sale from step 3, click it to
   see the line-item detail (parent/child `InvoiceList` → `InvoiceDetail`).
7. **Dashboard (F6)** — Finish here: stock value, today/week/month revenue, top-selling
   products, and the low-stock alert list all reflect what just happened.

Worth calling out to a reviewer: every mutating request (`POST /products`,
`POST /sales`, `POST /inventory/adjust`) carries a `userId` supplied by the Angular
`AuthService` rather than a security context, per the spec's manual-auth constraint —
and the backend still refuses to let one user's action masquerade as another's, since
`userId` is resolved to a real `User` row and rejected if it doesn't exist.
